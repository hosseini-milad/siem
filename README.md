# بک‌اند SIEM — فاز اول

API پایتون با **FastAPI + MongoDB** برای دریافت و ذخیرهٔ لاگ. تمام عملیات داده از Swagger انجام می‌شود؛ نیازی به دستور کنسولی برای ثبت یا جست‌وجوی لاگ نیست. دستورات زیر فقط برای نصب و راه‌اندازی سرویس‌ها هستند.

این نسخه احراز هویت، هوش مصنوعی، Logstash، Elasticsearch یا Kibana ندارد. پنل مخزن `spectral_panel` تغییر نکرده است. MongoDB محل اصلی نگهداری داده است؛ Elasticsearch در فاز بعد نمای جست‌وجو خواهد بود و جای MongoDB را نمی‌گیرد.

## نصب و اجرا

پیش‌نیاز: Python 3.12 یا جدیدتر و Docker Compose با daemon فعال.

```bash
cd /workspace/siem
python -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/python -m pip install --no-deps -e .
docker compose up -d --wait mongodb
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

`requirements.lock` نسخه‌های دقیق محیط آزمایش‌شده، شامل ابزارهای تست را نگه می‌دارد. در محیط کلاد در صورت نیاز به کش قابل نوشتن، به pip گزینهٔ `--cache-dir /workspace/.pip-cache` بدهید.

در مرورگر همان سرور مسیر `/docs` روی پورت ۸۰۰۰ را باز کنید. مسیر `/` نیز به Swagger هدایت می‌شود و قرارداد OpenAPI در `/openapi.json` قرار دارد. فایل‌های رابط Swagger به‌صورت پیش‌فرض FastAPI از CDN بارگذاری می‌شوند و مرورگر برای آن‌ها به اینترنت نیاز دارد.

تنظیمات اختیاری را از `.env.example` در `.env` کپی کنید؛ پیش‌فرض اتصال `mongodb://127.0.0.1:27017` و دیتابیس `siem` است. متغیرهای `SIEM_MONGODB_URI` و `SIEM_MONGODB_DATABASE` نیز پشتیبانی می‌شوند. اطلاعات اتصال محرمانه را commit نکنید.

MongoDB فقط روی loopback منتشر می‌شود و داده‌ها در volume نام‌دار `siem_mongo_data` باقی می‌مانند. `docker compose down` داده‌ها را نگه می‌دارد؛ گزینهٔ `-v` داده‌ها را حذف می‌کند. این تنظیم توسعه‌ای بدون احراز هویت است؛ برای دسترسی بیرونی آماده نیست. برنامه هنگام شروع اتصال MongoDB و ایجاد ایندکس‌ها را بررسی می‌کند؛ اگر دیتابیس در دسترس نباشد شروع برنامه شکست می‌خورد.

## اولین کار با Swagger

۱. بخش **Health**، اکشن `GET /api/v1/health` را باز کنید و `Try it out` و سپس `Execute` را بزنید. نتیجه باید `status: ok` و `database: mongodb` باشد.

۲. در بخش **Logs**، اکشن `POST /api/v1/logs` را باز کنید و این ورودی را اجرا کنید:

```json
{
  "timestamp": "2026-11-16T10:00:00Z",
  "source": "firewall-01",
  "level": "WARNING",
  "message": "Connection denied",
  "attributes": {
    "source_ip": "192.0.2.10",
    "destination_ip": "192.0.2.20",
    "port": 22
  }
}
```

پاسخ `201` شامل دادهٔ ذخیره‌شده، `id` و زمان دریافت `received_at` است. هر درخواست موفق یک شناسهٔ جدید می‌سازد؛ ارسال مجدد حذف تکرار ندارد.

۳. `GET /api/v1/logs` را اجرا کنید تا رکورد ذخیره‌شده را از MongoDB بخوانید. با `source`، `level`، `start` و `end` فیلتر کنید. بازهٔ زمان روی `timestamp` رویداد اعمال می‌شود و دو سر بازه را شامل می‌شود. `limit` بین ۱ تا ۱۰۰ و `offset` بین صفر تا ۱۰۰۰۰۰ است. پاسخ `items`، `total`، `limit` و `offset` دارد و بر اساس زمان نزولی مرتب می‌شود.

۴. شناسهٔ پاسخ مرحلهٔ ۲ را در `GET /api/v1/logs/{log_id}` قرار دهید. شناسهٔ ناموجود `404` و ورودی نامعتبر `422` برمی‌گرداند.

۵. برای ورود گروهی، `POST /api/v1/logs/batch` را با بدنهٔ زیر اجرا کنید:

```json
{
  "events": [
    {
      "timestamp": "2026-11-16T10:00:00Z",
      "source": "router-01",
      "level": "INFO",
      "message": "Interface up",
      "attributes": {"interface": "eth0"}
    }
  ]
}
```

ورودی گروهی ۱ تا ۵۰۰ رویداد می‌پذیرد. همهٔ رویدادها پیش از نوشتن اعتبارسنجی می‌شوند؛ وجود ورودی نامعتبر باعث رد کل درخواست می‌شود. عملیات گروهی تراکنش چندسندی نیست: در خطای اتصال/نوشتن ممکن است بخشی ثبت شده باشد. پاسخ خطای دیتابیس `503` است؛ پیش از ارسال مجدد، رکوردها را بررسی کنید.

زمان ورودی باید timezone داشته باشد؛ ذخیره و خروجی UTC با دقت میلی‌ثانیهٔ MongoDB است. `source` و `message` خالی پذیرفته نمی‌شوند. سطح‌ها `DEBUG`، `INFO`، `WARNING`، `ERROR` و `CRITICAL` هستند. `attributes` یک شیء JSON سازگار با BSON تا ۱ MiB است. فیلدهای اضافی سطح اصلی رد می‌شوند. بدنهٔ بسیار بزرگ باید در استقرار آینده در reverse proxy محدود شود.

## تست

با MongoDB فعال:

```bash
.venv/bin/python -m pytest -q
```

تست‌ها از دیتابیس‌های موقت مستقل `siem_test_<uuid>` استفاده می‌کنند و پس از اجرا همان دیتابیس‌ها را حذف می‌کنند. تنظیم اتصال تست از متغیرهای محیط/`.env` خوانده می‌شود؛ از سرور توسعه استفاده کنید. دادهٔ دیتابیس اصلی `siem` توسط تست حذف نمی‌شود.

فاز اول فقط ورود JSON ساختاریافته و مشاهده را پوشش می‌دهد. فایل CSV، syslog، ویرایش/حذف لاگ، تشخیص تهدید، هشدار و اتصال پنل هنوز پیاده نشده‌اند.

## ورود دیتاست از پوشه در Swagger

داده‌های واقعی را در ریشهٔ پروژه زیر `ds/Datasets` قرار دهید؛ مثلاً `ds/Datasets/Benign/Benign.csv.gz.001` و قسمت‌های بعدی. این فایل‌ها در Git قرار نمی‌گیرند. پیش‌فرض نام دیتابیس همچنان **siem** است و این ویژگی داده‌ها را در collection مستقل `dataset_records` و وضعیت اجرا را در `dataset_imports` نگه می‌دارد؛ قرارداد لاگ‌های قبلی تغییر نکرده است.

برای مسیر تصویر روی Windows، در فایل `.env` می‌توانید تنظیم کنید:

```dotenv
SIEM_DATASETS_ROOT=F:/PY/Server/SIEM/ds/Datasets
SIEM_MONGODB_DATABASE=siem
```

سرویس را بعد از تغییر تنظیمات دوباره اجرا کنید. مسیر، مسیر روی **سرور بک‌اند** است؛ انتخاب پوشه در Swagger فایل‌های کامپیوتر مرورگر را آپلود نمی‌کند. برای اجرای Linux باید پوشه به همان سرور منتقل یا mount شده و مسیر آن تنظیم شود.

در Swagger بخش **Datasets**:

1. `GET /api/v1/datasets/folders` را اجرا کنید تا نام پوشه‌های موجود را ببینید.
2. `POST /api/v1/datasets/imports` را با `{"folder":"Benign"}` اجرا کنید. مقدار `folder` را از فهرست مرحلهٔ قبل وارد کنید (فیلد متنی Swagger است، نه dropdown پویا). پاسخ `202` شناسهٔ اجرا را می‌دهد؛ عملیات در پس‌زمینه ادامه پیدا می‌کند.
3. با `GET /api/v1/datasets/imports/{import_id}` وضعیت `running`، `completed`، `failed` یا `interrupted` و شمارنده‌های `processed` و `inserted` را ببینید.
4. با `GET /api/v1/datasets/records` ردیف‌های واقعاً ذخیره‌شده را مشاهده کنید؛ صفحه‌بندی با `limit` و `offset` انجام می‌شود.

فرمت‌های پشتیبانی‌شده `.csv`، `.csv.gz` و gzip تقسیم‌شده به `.csv.gz.001`، `.002` و … هستند. تمام قسمت‌ها باید موجود و پیوسته باشند؛ آخرین قسمتِ مفقود فقط هنگام خواندن/بررسی صحت gzip قابل تشخیص است. قسمت‌ها به ترتیب به یک جریان متصل می‌شوند، نه اینکه هر قسمت مستقل gzip فرض شود. فایل ZIP/RAR پشتیبانی نمی‌شود. پوشه‌ها فقط یک سطح زیر ریشه بررسی می‌شوند؛ symlink فایل و خروج از ریشه پذیرفته نمی‌شود.

CSV باید UTF-8 (با یا بدون BOM)، با جداکنندهٔ کاما و header یکتا و غیرخالی باشد. چون نمونهٔ محتوای CSV در اختیار نیست، ستون‌ها با نام و مقدار اصلی و به‌صورت **رشته** مستقیماً در ریشهٔ سند ذخیره می‌شوند؛ هنوز تبدیل نوع، نرمال‌سازی یا تشخیص ستون label انجام نمی‌شود. اطلاعات جانبی پوشه، فایل، شمارهٔ ردیف، زمان دریافت و شناسهٔ اجرا در `dataset_records` ذخیره نمی‌شوند. فقط ستون‌های CSV و `_id` الزامی MongoDB وجود دارند؛ ستون ورودی با نام `_id` رد می‌شود. فیلتر پوشه از اکشن records حذف شده است. وضعیت عملیات همچنان در collection جداگانهٔ `dataset_imports` نگهداری می‌شود. برای تطبیق با فرمت دیگر، نمونهٔ header و چند سطر لازم است.

خواندن جریانی و نوشتن در batchهای ۵۰۰تایی است؛ فایل فشرده پیش از ورود برای شناسهٔ ثابت SHA-256 یک بار خوانده می‌شود. ارسال مجدد همان فایل با همان نام در همان پوشه ردیف‌های تکراری ایجاد نمی‌کند؛ تغییر محتوا یا نام فایل ورودی جدید محسوب می‌شود. در خطا batchهای قبلی باقی می‌مانند و اجرای مجدد فایل ثابت امکان ادامه با رد ردیف‌های موجود را فراهم می‌کند. شمارنده‌های خطای نوشتن شبکه ممکن است آخرین batch نامطمئن را منعکس نکنند؛ برای بررسی قطعی از records استفاده کنید.

این worker درون فرایند است: فعلاً سرور را با **یک worker و بدون reload حین ورود** اجرا کنید. هر بار یک ورود مجاز است؛ درخواست همزمان `409` می‌گیرد. شروع مجدد سرور اجرای نیمه‌تمام را `interrupted` می‌کند؛ پس از آن دوباره همان پوشه را ارسال کنید. برای پردازش توزیع‌شده/صف پایدار بعداً worker مجزا نیاز است. سلامت gzip بررسی می‌شود، اما یک فایل خراب ممکن است پیش از کشف خطا چند batch ذخیره کرده باشد.

## نرمال‌سازی کل دیتاست

در Swagger بخش **Normalization**، `POST /api/v1/normalization/runs` را بدون بدنه اجرا کنید. در نخستین اجرا آمار مشترک و واژگان دسته‌ها محاسبه و ثابت ذخیره می‌شوند؛ در تمام اجراها فقط رکوردهایی که `original_id` آن‌ها در `normal_records` وجود ندارد تبدیل می‌شوند. وضعیت و پارامترهای تبدیل با `GET /api/v1/normalization/runs/{run_id}` و خروجی با `GET /api/v1/normalization/records` قابل مشاهده‌اند. دادهٔ اصلی تغییر نمی‌کند.

قواعد تبدیل:

- `Source File` (بدون حساسیت به بزرگی حروف و فاصلهٔ ابتدا/انتها) حذف می‌شود. شناسهٔ منبع در `original_id` حفظ و همان مقدار برای `_id` خروجی استفاده می‌شود. این دو شناسه ویژگی عددی مدل نیستند.
- ستون‌های عددی، از جمله پورت‌ها و Timestamp عددی نمونه، با `(x-min)/(max-min)` روی **کل مجموعه** به بازهٔ صفر تا یک تبدیل می‌شوند. ستون ثابت یا کاملاً خالی صفر می‌شود. مقادیر به‌صورت عدد در MongoDB ذخیره می‌شوند، نه رشته.
- `Src IP` و `Dst IP` با استاندارد آدرس IP به عدد صحیح تبدیل و بر بیشینهٔ فضای IPv4 یا IPv6 تقسیم می‌شوند. خروجی صفر تا یک است؛ این تبدیل مفهوم فاصلهٔ شبکه را مدل نمی‌کند و در IPv6 دقت float ممکن است آدرس‌های نزدیک را یکسان کند. IP نامعتبر اجرای کار را متوقف می‌کند.
- `Protocol` حتی اگر به شکل عدد باشد، متغیر اسمی است و One-Hot می‌شود. ستون‌های متنی دیگر نیز One-Hot می‌شوند: مثلاً `Protocol__category_0`. نگاشت دقیق مقدار اصلی به نام ستون در `schema` پاسخ وضعیت اجرا ثبت می‌شود. بیش از ۲۵۶ دسته برای هر ستون رد می‌شود تا ستون شناسهٔ پرتنوع تصادفاً به هزاران ویژگی تبدیل نشود.
- `Label` با حذف فاصله و بدون حساسیت به حروف: `benign`، `normal` و `0` → عدد **۰**؛ نام‌های دیگر حمله و `1` → **۱**. برچسب خالی یا `unknown`/`unlabeled` خطاست؛ از نام پوشه به‌جای برچسب استفاده نمی‌شود. نام کلاس حمله در دادهٔ اصلی باقی می‌ماند.
- مقدار خالی، ستون غایب، `NaN`، `None`، `null` و Infinity مقدار گمشده محسوب و در خروجی صفر می‌شوند. آمار عددی بدون این مقادیر محاسبه می‌شود. برای دستهٔ گمشده همهٔ بیت‌ها صفر است. صفرگذاری یک سیاست صریح برای این نسخه است؛ صفر خروجی لزوماً صفر واقعی ورودی نیست.

تمام ویژگی‌های خروجی عددی در بازهٔ صفر تا یک هستند؛ نام ستون‌ها حفظ می‌شود مگر ستون متنی که به ویژگی‌های One-Hot تبدیل می‌شود. ورودی nested و نام ستون ناسازگار با خروجی MongoDB رد می‌شود. پردازش جریانی با batchهای ۵۰۰تایی است. پارامترهای تبدیل و وضعیت اجرا در collection مستقل `normalization_runs` قرار می‌گیرند و به اسناد `normal_records` اضافه نمی‌شوند.

پارامترهای ثابت در `normalization_parameters` ذخیره می‌شوند. برای ارتقا از نسخهٔ قبلی، schema آخرین اجرای موفق از `normalization_runs` بازیابی می‌شود؛ اگر خروجی قدیمی وجود داشته باشد ولی schema متناظر پیدا نشود، اجرا با خطای واضح متوقف می‌شود تا مقیاس داده‌ها مخلوط نشود. این collectionها را حذف نکنید. `processed` تعداد رکورد تازه درج‌شده در همین اجرا و `skipped` تعداد رکوردهای از قبل موجود است. اجرای دوباره بدون دادهٔ جدید `processed=0` دارد. رکوردهای موجود حتی در صورت تغییر منبعشان بازنویسی نمی‌شوند و حذف منبع نیز خروجی قدیمی را حذف نمی‌کند.

مقادیر عددی جدید با همان Min-Max قبلی تبدیل و در صورت خروج از محدوده به صفر/یک clip می‌شوند؛ ستون ثابت همچنان صفر می‌ماند. دستهٔ متنی جدید با بردار تمام‌صفر نمایش داده می‌شود و واژگان قبلی را تغییر نمی‌دهد. ستون کاملاً جدید خطاست و نیاز به تصمیم مستقل برای بازسازی schema دارد. خروجی قبلی حذف یا جایگزین نمی‌شود؛ batchهای موفق ۵۰۰تایی باقی می‌مانند و پس از خطا/توقف، اجرای مجدد آن‌ها را رد می‌کند. ممکن است در خطای شبکه شمارندهٔ آخرین batch نامطمئن باشد؛ رکوردهای واقعی مرجع هستند.

فقط با یک worker اجرا کنید و هنگام پردازش، منبع را از خارج برنامه تغییر ندهید. ورود دیتاست و نرمال‌سازی در همین فرایند همزمان مجاز نیستند. اگر اکنون نسخهٔ قبلی در حال نرمال‌سازی است، بگذارید اجرای آن کامل شود، سپس کد را دریافت و سرویس را دوباره اجرا کنید؛ به حذف داده‌ها نیازی نیست.

این اکشن بنا به درخواست، آمار کل مجموعه را به کار می‌برد. برای آموزش و ارزیابی مدل در آینده باید ابتدا train/test جدا شوند و پارامترهای تبدیل فقط از train یاد گرفته شوند تا نشت اطلاعات رخ ندهد. فایل واقعی کاربر در محیط توسعه موجود نیست؛ آزمون‌ها با نمونه‌های مصنوعی و MongoDB واقعی اجرا شده‌اند.

### پیگیری توقف یا کندی نرمال‌سازی

پاسخ `202` فقط پذیرش درخواست است. شناسهٔ `id` همان پاسخ را در `GET /api/v1/normalization/runs/{run_id}` وارد کنید؛ ممکن است سندی که از قبل در دیتابیس می‌بینید متعلق به اجرای قبلی باشد.

در اجرای نخست، مرحلهٔ `fit` تمام ورودی را برای محاسبهٔ Min-Max می‌خواند و تا پایان آن رکوردی در خروجی تولید نمی‌شود؛ بنابراین `processed=0` در این مرحله طبیعی است. `scanned` تعداد ورودی‌های بررسی‌شده و `heartbeat_at` زمان آخرین پیشرفت است. این اطلاعات برای اولین رکورد، تقریباً هر پنج ثانیه در طول پردازش و پایان fit ذخیره و در کنسول چاپ می‌شوند. هنگام انتظار برای پاسخ MongoDB یا ساخت ایندکس ممکن است heartbeat به‌روز نشود؛ نبود heartbeat به تنهایی تشخیص قطعی توقف نیست. در مرحلهٔ transform شمارنده‌ها پس از هر batch ذخیره می‌شوند.

لاگ‌های `Normalization <id> accepted/started/fit/transform/completed` شناسهٔ همان اجرا را دارند. خطاها با traceback در کنسول و `status=failed`، `error` و `error_type` در وضعیت اجرا ثبت می‌شوند. اگر دیتابیس برای ثبت خطا هم در دسترس نباشد، این اتفاق در کنسول گزارش می‌شود.

`interrupted` توسط راه‌اندازی سرور برای اجراهای قبلی با وضعیت running ثبت می‌شود؛ `interrupted_at` و `interruption_reason` علت ثبت این وضعیت را توضیح می‌دهند. این نشانهٔ کشف خطای CSV نیست. برای جلوگیری از علامت‌خوردن اجرای فعال توسط فرایند دیگر، فقط یک نمونه از سرور با یک worker و بدون `--reload` اجرا کنید:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1 --log-level info
```

کارهای پس‌زمینه صف پایدار مستقل نیستند؛ پس از restart باید اکشن را دوباره اجرا کنید. رکوردهای خروجی موجود رد می‌شوند؛ اگر هنوز اولین fit تمام نشده باشد، محاسبهٔ آمار از ابتدا انجام می‌شود.

### تنظیم زمان انتظار MongoDB

مهلت دریافت پاسخ (`socketTimeoutMS`) به‌صورت پیش‌فرض ۶۰ ثانیه است. برای عملیات طولانی می‌توانید مقدار آن را در `.env` یا متغیر محیط تغییر دهید (مقادیر به میلی‌ثانیه‌اند):

```dotenv
SIEM_MONGODB_SOCKET_TIMEOUT_MS=120000
SIEM_MONGODB_CONNECT_TIMEOUT_MS=3000
SIEM_MONGODB_SERVER_SELECTION_TIMEOUT_MS=3000
```

مقادیر منفی پذیرفته نمی‌شوند؛ صفر طبق رفتار PyMongo یعنی انتظار بدون محدودیت. پس از تغییر تنظیمات، سرویس را دوباره اجرا کنید. در مسیر پردازش نرمال‌سازی شمارش دقیق کل ورودی انجام نمی‌شود؛ `total` و `total_estimate` از همان تخمین اولیهٔ MongoDB استفاده می‌کنند و ممکن است با شمارش نهایی متفاوت باشند. شمارنده‌های `processed` و `skipped` همچنان حاصل پردازش واقعی‌اند. پارامترهای Fit ذخیره‌شده و ردکردن `original_id`های موجود تغییری نکرده‌اند.

## ویژگی‌های رفتاری بلوک‌های ۱۰۰۰۰ رکوردی

پس از تکمیل نرمال‌سازی، در Swagger بخش **Standardization**:

1. `POST /api/v1/standardization/runs` را بدون بدنه اجرا کنید.
2. با `GET /api/v1/standardization/runs/{run_id}` وضعیت و شمارنده‌های `processed` و `blocks` را ببینید.
3. `GET /api/v1/standardization/records` خروجی `standard_records` را با صفحه‌بندی نشان می‌دهد؛ `total` تخمینی است.

ورودی `normal_records` با ترتیب صعودی `_id` خوانده و به بلوک‌های مستقل و غیرهم‌پوشان **۱۰۰۰۰ رکوردی** تقسیم می‌شود؛ آخرین بلوک ناقص هم پردازش می‌شود. این ترتیب قطعی است، اما الزاماً ترتیب زمان رویداد یا ترتیب شمارهٔ سطر CSV نیست. هر بلوک می‌تواند مدت زمانی متفاوت داشته باشد و هیچ آماری از بلوک مجاور به آن منتقل نمی‌شود. این روش پردازش آفلاین کل بلوک است، نه پنجرهٔ یک‌دقیقه‌ای یا تشخیص آنلاین علّی. شمارش رکورد به معنی شمارش درخواست یا بسته نیست.

تمام فیلدهای هر سند نرمال‌شده، شامل `_id`، `original_id`، `Label` و ویژگی‌های One-Hot، بدون تغییر کپی می‌شوند. پیوند به دادهٔ اصلی همچنان **`dataset_records._id == original_id`** است. اطلاعات IP، پورت، Timestamp و حجم از سند اصلی خوانده می‌شود؛ از IP و زمان نرمال‌شده برای محاسبه استفاده نمی‌شود. پارامترهای Fit و collectionهای قبلی تغییر نمی‌کنند.

ویژگی‌های جدید در شیء `behavior_features` قرار دارند:

| فیلد | معنا در همان بلوک |
| --- | --- |
| `block_index`, `block_size` | شمارهٔ بلوک از صفر و تعداد واقعی رکوردهای آن |
| `block_duration_seconds`, `block_timestamp_samples` | فاصلهٔ بیشینه و کمینهٔ زمان معتبر و تعداد زمان‌های معتبر |
| `source_record_count`, `source_record_share` | تعداد رکوردهای همان مبدأ، شامل رکورد جاری، و سهم آن از کل بلوک |
| `destination_record_count` | تعداد رکوردهای همان مقصد |
| `source_destination_record_count` | تعداد رکوردهای همان زوج مبدأ و مقصد |
| `source_unique_destination_count` | تعداد IP مقصد یکتا برای مبدأ |
| `source_unique_destination_port_count` | تعداد پورت مقصد یکتا برای مبدأ |
| `destination_unique_source_count` | تعداد مبدأ یکتا برای مقصد |
| `source_interarrival_mean_seconds`, `source_interarrival_std_seconds` | میانگین و انحراف معیار جامعهٔ فاصله‌ها پس از مرتب‌سازی زمان‌های همان مبدأ در بلوک |
| `source_timestamp_samples` | تعداد زمان‌های معتبر همان مبدأ؛ کمتر از دو نمونه یعنی فاصله‌ها صفر گزارش می‌شوند |
| `source_total_bytes`, `source_byte_samples` | مجموع بایت‌های رفت و برگشت مبدأ و تعداد رکوردهای دارای هر دو مقدار معتبر |
| `source_total_packets`, `source_packet_samples` | مجموع بسته‌های رفت و برگشت مبدأ و تعداد رکوردهای دارای هر دو مقدار معتبر |
| `source_ip_available`, `destination_ip_available`, `timestamp_available` | پرچم صفر/یک وجود مقدار معتبر برای رکورد جاری |

نام ستون‌ها بدون حساسیت به حروف و فاصلهٔ ابتدا/انتها خوانده می‌شود: `Src IP`/`Source IP`، `Dst IP`/`Destination IP`، `Dst Port`/`Destination Port` و `Timestamp`. Timestamp باید Unix برحسب **ثانیه** باشد؛ زمان متنی یا غیرمتناهی نامعتبر محسوب می‌شود. IP/پورت گمشده وارد مجموعه‌های یکتا نمی‌شود و IPهای گمشده با هم یک میزبان فرض نمی‌شوند.

حجم از `TotLen Fwd Pkts` و `TotLen Bwd Pkts` یا `Total Length of Fwd Packets` و `Total Length of Bwd Packets` استخراج می‌شود. تعداد بسته از `Tot Fwd Pkts` و `Tot Bwd Pkts` یا `Total Fwd Packets` و `Total Backward Packets` است. برای هر رکورد باید هر دو جهت عدد متناهی و نامنفی باشند. نبود داده با شمارندهٔ نمونهٔ صفر مشخص می‌شود؛ صفر حجم بدون توجه به شمارندهٔ نمونه قابل تفسیر نیست. نرخ شکست اتصال به دلیل نبود قرارداد معتبر برای وضعیت اتصال ساخته نمی‌شود.

ویژگی‌های جدید آمار خام‌اند و الزاماً در بازهٔ صفر تا یک نیستند؛ برای آموزش بعدی، مقیاس‌بندی آن‌ها باید جداگانه و فقط بر اساس train انجام شود. `block_index` و شمارنده‌های کیفیت داده بیشتر برای پیگیری‌اند و لزوماً ورودی مناسب مدل نیستند. هیچ برچسبی برای محاسبهٔ آمار استفاده نمی‌شود. هنگام ارزیابی، بلوک‌ها را کامل بین train/test جدا کنید تا زمینهٔ مشترک بلوک نشت نکند.

اجرای مجدد همهٔ بلوک‌ها را دوباره محاسبه و اسناد `standard_records` را با همان شناسه جایگزین می‌کند؛ تکرار، سند مضاعف نمی‌سازد. بنابراین اضافه‌شدن داده و تغییر مرز بلوک، آمار قبلی را پس از اجرای **موفق کامل** اصلاح می‌کند. این عملیات تراکنش سراسری نیست: در خطا، خروجی batchهای قبلی باقی می‌ماند و باید اجرا را تکرار کنید. خواندن خروجی برای آموزش را تا وضعیت `completed` به تعویق بیندازید. حذف رکورد از ورودی، خروجی قدیمی آن را خودکار حذف نمی‌کند؛ این نسخه برای دیتاست ثابت یا افزایشی است.

اگر سند اصلی موجود نباشد یا ورودی از قبل فیلد رزروشدهٔ `behavior_features` داشته باشد، بلوک با خطای واضح متوقف می‌شود تا دادهٔ قبلی بازنویسی ناخواسته نشود. اجرا با ورود دیتاست و نرمال‌سازی قفل مشترک دارد. فقط یک فرایند با یک worker و بدون reload اجرا کنید و طی پردازش از بیرون برنامه منبع را تغییر ندهید. شروع مجدد سرور کار نیمه‌تمام را `interrupted` می‌کند؛ برای بازسازی دوباره اکشن را اجرا کنید.
